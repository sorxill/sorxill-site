# /commit

## Процесс

1. `git status` и `git diff` (staged и unstaged) — понять, что изменилось.
2. Если в изменениях больше одной логической правки — предложить разбить на несколько коммитов и дождаться решения.
3. Стейджить конкретные файлы. **Никогда `git add -A`** — в репозиторий не должны попасть `.env` и локальные артефакты.
4. Прогнать `make lint` для затронутого приложения. Если падает — не коммитить, сообщить об ошибках.
5. Сформировать сообщение и закоммитить.

## Формат

```
<type>(<scope>): <заголовок в нижнем регистре, без точки, до 60 символов>

<опционально: 1-3 пункта — ЧТО изменилось и ЗАЧЕМ>
```

Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`.
Скоупы этого проекта: `api`, `web`, `domain`, `infra`, `ci`, `docs`, `design`.

## Правила

- Заголовок отвечает на «что делает этот коммит», а не «что я потрогал».
  Хорошо: `perf(api): кэшировать список проектов в redis`.
  Плохо: `fix stuff`, `обновил файлы`, `wip`.
- Тело нужно, когда решение неочевидно: пиши **почему**, а не пересказывай диф.
- Ломающее изменение API или схемы БД → `feat(api)!:` и блок `BREAKING CHANGE:` в теле.
- Если изменение — архитектурное решение, напомнить, что нужен ADR в `docs/adr/`.
- Не добавлять строки атрибуции AI: история коммитов публикуется на странице
  изменений сайта, лишний шум там не нужен.
