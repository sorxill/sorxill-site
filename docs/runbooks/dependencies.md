# Runbook: что делать с PR от Dependabot

## Правило одной строки

**Патчи и миноры** — мерджить по зелёному пайплайну не читая диф.
**Мажоры** — читать changelog, мерджить по одному, каждый отдельно.

Отличить просто: мажор меняет первую цифру (`vitest 2 → 4`, `mypy 1 → 2`).

## Порядок

1. Дождаться зелёного пайплайна на PR. Красный — не мерджить, а разбираться:
   Dependabot честно показал, что обновление ломает проект.
2. Мажоры мерджить **по одному** и с паузой. Если после трёх сразу что-то отвалится,
   вы не будете знать, из-за какого.
3. После мержа мажора прогнать локально `make lint && make test` — CI покрывает не всё,
   например `next build` с реальным контентом.

## Что требует особого внимания в этом проекте

| Пакет | Почему осторожно |
|---|---|
| `typescript` мажор | Тянет за собой `eslint-config-next` и типы Next. Мерджить только когда обе зависимости объявили поддержку |
| `eslint` мажор | Ломает flat-конфиг. `eslint-config-next` обязан поддерживать новую версию, иначе линт упадёт целиком |
| `next` мажор | Ломающие переименования вроде `middleware.ts` → `proxy.ts`. Читать upgrade guide, использовать `npx @next/codemod upgrade` |
| `next-intl` мажор | Жёстко привязан к версии Next. Обновлять вместе с ним, не раньше |
| `mypy` мажор | Новый мажор находит ошибки, которых раньше не видел. Это не поломка, а работа — заложите время |
| `postgres` в Dockerfile | Мажор Postgres требует миграции данных, `docker pull` этого не сделает. **Никогда не мерджить не глядя** |

## Про npm audit

`npm audit` после установки показывает уязвимости во **всех** зависимостях, включая
инструменты разработки, которые не попадают в продакшен-образ. Прежде чем пугаться:

```bash
npm audit --omit=dev        # только то, что реально уедет к пользователям
```

Обычно этот список пуст или короткий. Уязвимость в `vitest` или в сборщике
не эксплуатируется через ваш сайт — там нет ни одного байта этого кода.
Что действительно смотрит на прод — Trivy по собранному образу в пайплайне,
и он падает на HIGH/CRITICAL.

⚠️ `npm audit fix --force` не запускать. Он ставит мажоры в обход всех проверок
совместимости и ломает проект чаще, чем чинит.

## Ежемесячный ритуал, 15 минут

```bash
git pull
gh pr list --label dependencies
# зелёные патч-PR — merge
# мажоры — по одному, читая changelog
```

Не накапливайте. Пять пропущенных месяцев превращаются в один болезненный день,
и в этот момент обычно оказывается, что обновление безопасности приехало вместе
с четырьмя ломающими изменениями.

## Разбор аудита от 30.07.2026: как читать эти 17 записей

Первый `npm audit` показал 17 уязвимостей и напугал. Реальную угрозу представляла
одна. Разбор оставлен как образец: следующий отчёт читается по той же схеме.

| Что | Где живёт | Работает ли в проде | Что сделали |
|---|---|---|---|
| `sharp` / libvips, 4 CVE, high | оптимизация изображений в Next | **да** — единственная настоящая | Пин `^0.35.3` + `overrides`, чтобы поднялась и вложенная копия внутри Next |
| `esbuild` dev-сервер, moderate | vite → vitest | нет, только локальный запуск тестов | Апгрейд `vitest` до 4 |
| `brace-expansion` / `minimatch`, high | eslint и его плагины | нет, линтер в образ не попадает | Ждём `eslint` 10 через Dependabot, когда `eslint-config-next` объявит поддержку |
| `postcss`, high | вложенная копия внутри Next | формально да, практически нет | Ждём патч от Next. Эксплуатируется через обработку **чужого** CSS на сборке, а весь наш CSS свой |

## Как разбирать следующий отчёт

1. `npm audit --omit=dev` — отсекает всё, чего нет в продакшен-образе. Обычно это
   две трети списка.
2. `npm ls <пакет>` — понять, чья это зависимость и есть ли вложенная копия.
3. Спросить себя: **достижим ли этот код от посетителя сайта?** Уязвимость в
   dev-сервере vite не достижима — на сервере vite нет.
4. Если пакет вложенный и апстрим ещё не выпустил патч — `overrides` в
   `package.json`. Это именно тот случай, для которого поле существует.
5. Trivy в пайплайне сканирует **собранный образ** — вот его находки надо чинить
   всегда, там нет ничего лишнего.

⚠️ `npm audit fix --force` не запускать никогда. В этом самом отчёте он предлагал
«починить» postcss установкой `next@9.3.3` — то есть откатить фреймворк с 16-й
версии на 9-ю. Автоматика не понимает, что уязвимость вложенная.

## Как теперь выкатывается версия (ADR-0018)

```bash
git push                       # → checks.yml, 2-3 минуты, ничего не деплоится
# накопили изменений, готовы показать людям:
gh pr list --label "autorelease: pending"   # релизный PR от release-please
gh pr merge <номер> --squash                # → создаётся тег vX.Y.Z
                                            # → release.yml собирает образы и деплоит
```

Откат без нового релиза:

```bash
gh workflow run release.yml -f rollback_sha=<sha предыдущего релиза>
```

## Раз в месяц: Security → Code scanning

Trivy больше не блокирует релиз, поэтому находки надо смотреть самому.
Вкладка Security в репозитории, категории `trivy-api` и `trivy-web`.

Разбирать по тому же принципу: **достижим ли код от посетителя сайта.**
CVE в npm базового образа — нет (npm из рантайм-образа удалён).
CVE в `sharp` — да, чинить сразу.
