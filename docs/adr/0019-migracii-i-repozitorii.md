# ADR-0019: SQLAlchemy-репозиторий под существующий контракт

**Дата:** 2026-07-30 · **Статус:** принято

## Контекст

M0 работал на in-memory репозитории. Нужно было перейти на Postgres, не сломав
уже написанные use cases и не переписывая тесты.

## Решение

Реализовать `SqlAlchemyProjectRepository` под тот же `Protocol`, что и in-memory,
и включить его в существующий параметризованный набор контрактных тестов.
Схема создаётся Alembic-миграцией, инварианты продублированы `CHECK`-ограничениями.

**Проверка, ради которой всё и затевалось:** переход не потребовал ни одной правки
в `app/application/` и `app/domain/`. Изменился только `app/api/deps.py` — место,
где выбирается реализация. Это и есть практический смысл DIP, а не теория из книги.

## Альтернативы

| Вариант | Почему не он |
|---|---|
| Работать с ORM-моделями прямо в use cases | Домен узнал бы про SQLAlchemy, `import-linter` бы это запретил, а тесты потребовали бы базу |
| Repository поверх ORM без контрактных тестов | Тогда расхождение поведения двух реализаций всплыло бы в проде |
| SQLModel вместо SQLAlchemy | Смешивает модель БД и схему API в одном классе — ровно та связанность, от которой мы уходим |
| Тесты API тоже на Postgres | Медленно и не нужно: HTTP-слой проверяется на in-memory, работа с БД — контрактными тестами |

## Последствия

**Стало лучше:** `readyz` теперь действительно проверяет базу — раньше он врал, и
`rollout.sh` считал бы контейнер здоровым, пока приложение не работает.
Миграции проверяются в CI циклом upgrade → downgrade → upgrade.

**Цена:** тесты требуют Postgres. Без `DATABASE_URL` контрактные тесты для
SQLAlchemy молча пропускаются — в CI сервис поднят, локально нужен `make dev`.
Это компромисс: альтернатива — обязательный Docker для запуска любого теста.

**Мина на будущее:** `lazy="selectin"` на переводах проектов стоит не для красоты.
Без него список из 20 проектов даст 21 запрос к базе. При добавлении новых связей
проверяйте это в первую очередь — на 2 ядрах N+1 заметен сразу.
